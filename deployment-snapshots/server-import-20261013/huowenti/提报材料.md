## 一、核心创作思路与目标用户

### 1.1 我们看到的那个缺口

有一类问题，搜索引擎和生成式 AI 结构性地答不了，因为它缺的不是知识，而是**当事人**：

> 「2027 届普通本科生找第一段 AI 产品实习到底有多难？」

公开内容里有大量方法和建议——「简历要怎么写」「面试怎么准备」「项目要有数据」。但这些内容有一个共同的空洞：**它们不包含一个具体的人从投递到被拒或被录用的完整经过**。没有人写清自己投了多少份、卡在第几轮、招聘方当时到底看了什么。

更关键的是，这类问题的答案散落在不同位置的人手里：

- **经历过失败的人**知道卡在哪一步，但他们的失败过程通常不会被写出来；
- **招聘一侧的人**知道筛选的真实顺序，但他们几乎不会公开讲；
- **同一个项目**在不同类型公司得到的反馈可能完全相反，但没人把这两种结果放在一起比过。

**缺的不是更多建议，而是真正经历过这件事的人。** 这是当前 AI 能力边界之外、但知乎社区刚好能补上的一块。

### 1.2 创作思路

我们没有让 AI 去编一个「看起来合理」的答案，而是把「谁真的经历过这件事」变成一条**可以主动找到人、可以交叉比较、可以逐条核对**的链路：

> 系统负责把问题拆清楚、把已知和未知分开、把读不到的部分显式标出来；答案由真正经历过的人提供，每一条都带身份、时间和可核对的事实，并且会随着新经历进入而更新。

这个产品的名字叫**活问题**：一个会主动寻找回答者的问题。

### 1.3 目标用户

**提问者（也是本作品的核心用户）**：正在面对一个具体、有明确人群和阶段、但公开内容答不清楚的问题的人。首版聚焦在一个真实且高频的场景——**在校生找第一段 AI 产品实习**。

**回答者**：经历过这件事的当事人。产品按位置把他们分成四类，问题只会问他们知道的那一部分：

| 参与身份 | 他们独有的信息 |
| --- | --- |
| 我已经拿到实习或进入面试 | 成功的路径、面试官实际追问了什么 |
| 我投递过，但没有结果 | 失败的完整过程、卡在哪一步 |
| 我正在找第一段 AI 产品实习 | 当前的需求与卡点 |
| 我参与过招聘或面试 | 筛选的真实顺序、实际会看哪些信息 |

**为什么选这个场景**：它同时满足三个条件——问题足够具体（能拆成可比较的条件）、公开内容明显不足（能验证缺口真实存在）、当事人分布清楚（求职者与招聘方都能被找到）。

## 二、用户如何完成核心体验（八步闭环）

```text
① 活问题现场    一个问题，先展示它现在能回答到什么程度
② 三个缺口      把「读不到的部分」逐条标出来，作为去找人的理由
③ 参与采访      按位置选身份，问题只问那一部分
④ 追问          针对刚填的内容，追一个只有当事人能回答的问题
⑤ 贡献确认      生成一张贡献卡，用户确认后才会进入调查
⑥ 问题变化      这份经历让哪一条子命题的覆盖状态变了
⑦ 当前调查结论  六条子命题各自的证据状态、相反经历与仍未解决
⑧ 知乎回答      把当前调查整理成一份可编辑、可复制的回答草稿
```

**用户实际会看到和操作的（线上真实流程）**：

1. **活问题现场**：首页直接给出母问题「2027 届普通本科生找第一段 AI 产品实习到底有多难？」，并说明它现在能回答到什么程度——**公开内容已经说了什么**、**仍然读不到的部分**、**这个问题在找谁**。
2. **三个缺口**：页面列出三条实际检索出来的空白——普通本科无实习者的完整失败过程、招聘参与者对筛选的具体说明、同一种项目在不同公司类型的实际结果差异。每一条都写明它对应哪几条子命题。
3. **三维图谱**：页面主体是一张**时间 × 子命题 × 内容数量**的三维图。横轴是时间（左半段是更早的公开来源，右半段是当前调查区间），纵轴是六条子命题，高度是这一格里有多少条内容。**每颗星都是一条可以点开核对的内容**；密度微光只表示「这一格内容多」，不可点击、不计入统计。
4. **参与采访**：用户点「回答一个只有你知道的问题」，先选一个最接近自己的位置（四类身份），然后只回答属于那一部分的 5 至 6 个问题。
5. **追问**：提交后，系统会针对**刚填的具体内容**再追问一句（例如用户提到一个数字，就问「这个数字是从哪里得到的」）。这是为了让内容可被核对，而不是收一份自述。
6. **贡献确认**：生成一张贡献卡，逐条列出用户提供的事实并标注来源。页面明确写着「这是一份个人经历，不代表行业整体情况」「不会自动发布成知乎回答」「你可以随时删除它」。**用户确认后才会进入调查。**
7. **问题变化**：展示这份经历进入前后，六条子命题各自的覆盖状态发生了什么变化。变化为 0 的地方会如实说明这段经历没有触及那一条。
8. **当前调查结论 / 知乎回答**：结论页按六条子命题分别给出证据状态；「知乎回答」页把当前调查整理成一份**可以先修改的草稿**——草稿只由已确认的公开来源和当事人经历拼成，不添加任何未经验证的说法，也不会自动发布。

**六条子命题**（固定拆法，保证不同人的经历可以横向比较）：

```text
初始背景    学校背景、专业、已有实习和已有项目
项目经历    项目是否可运行、是否有真实用户、个人贡献是什么
投递过程    投递渠道、投递数量、目标公司类型
面试筛选    简历反馈、面试阶段、具体淘汰位置
公司差异    大厂、成熟公司和 AI 创业公司的判断差异
最终结果与失败过程  最好进度、Offer 情况、做过但没有产生效果的准备
```

**关键设计有三处**：

- **把「读不到」显式化**——首页和三维图都直接展示当前检索范围内**没有**找到什么。缺口不是营销话术，它是这个产品要去找人的理由。
- **按位置提问，不让人回答不属于自己的部分**——招聘一侧不会被问「你投了多少份」，求职者不会被问「你们怎么筛简历」。
- **结论与来源绑定，且区分证据强度**——每一格的证据状态只有四种，且都写清含义（见 3.2）。

## 三、整体技术方案

### 3.1 架构

- **前端**：原生 HTML / CSS / JS，零构建依赖，单页八个视图。三维图谱用 Three.js 绘制，页面**不引任何外部 CDN**，全部资源同源加载。
- **服务端**：Node + Express，负责语料获取与缓存、身份与采访流程、追问生成、覆盖度计算、图谱数据、回答草稿生成、限流与降级。
- **数据**：JSON 文件持久化，结构简单、可审计，便于赛事期间快速迭代与人工复核。
- **内容接口**：知乎黑客松免鉴权公开内容接口（故事 / 知识）；知乎开放平台搜索接口（可选，凭证仅存服务端）。
- **字体**：自托管分片字体（105 个 woff2，约 6.11MB），**不依赖任何第三方字体服务**，保证首屏无外部请求。

### 3.2 证据模型（产品核心）

可信度不是一个黑盒分数，而是四种可解释、可复核的状态，**按六条子命题分别计算**：

| 状态 | 含义 |
| --- | --- |
| `multi-case` 已有多份经历 | 已有多份个人经历，可以开始比较条件差异 |
| `single-case` 只有一份经历 | 只有一份个人经历，还不能说明普遍情况 |
| `public-only` 只有公开讨论 | 只有公开讨论，缺少当事人提供的完整过程 |
| `empty` 覆盖不足 | 当前检索范围内覆盖不足 |

**覆盖度计算口径一致**：同一套判据同时用于「地图上挂了哪些内容」和「提出新问题时判断这个领域够不够」——只有当内容**直接指向母问题**（在校生找第一段实习）时才算相关。泛职场内容（升职加薪、职业倦怠、职业发展）一律不计入，因为它们不回答这个问题。

**相反经历识别**：两份经历如果在「本科 / 大厂 / 创业公司 / 有真实用户」等条件上相近、结果却相反，会被自动标记为对照连线，提示「值得继续追问」，而不是取平均。

### 3.3 问题拆解这一步，我们不冒充大模型

新问题能不能启动，用的是**可解释的规则判定**：

- **边界判定**：问题太宽（出现「所有 / 一切 / 人生 / 社会」这类词，或没有具体限定）会先要求收窄，并给出改写示例。
- **具体度判定**：需要同时出现具体人群与具体阶段，才允许启动。
- **内容充分度判定**：与当前抓取到的公开内容逐条比对，已经足够充分的问题不会被重复启动。

这样做的原因是：这一步的目标是**把问题问清楚、把未知标出来**，不是生成结论。规则化实现完全可复现、可审计、不会凭空编造。规则表全部在开源仓库中，评委可以逐行核对。

### 3.4 动效与设计规范（可验证）

本作品的动效与页面设计遵循公开的 motion-web 设计规范，并已落到代码中、可被自动化验收检查：

- **时长阶梯 6 档**：instant 90ms / fast 170ms / standard 320ms / medium 460ms / slow 700ms / cinematic 1200ms。
- **真实弹簧缓动**：使用 CSS `linear()` 描述欠阻尼弹簧（stiffness 60–90、damping 0.86–0.93），入场有轻微过冲，不是生硬的线性动画。
- **帧率无关的跟随**：视角跟随按 `1-exp(-k·dt)` 计算，不随帧率变化。
- **滚轮惯性防护**：累积 90px 才触发、锁定 600ms、速度按 0.92 衰减。
- **静止时呼吸**：不同元素用不同频率的微光，避免整页同步闪烁。
- **reduced-motion 三级降级**：开启「减少动态效果」后，位移动画降为纯淡入、呼吸与微光停止、过渡全部关闭，**内容照常出现**。

**粒子是细小星光点，不是泡泡或球体**——这是硬约束，图上每个可点元素都是星光点，没有玻璃珠质感。

**当前公开内容底账 30 条**，均来自官方接口，保留来源字段，不做长文全文搬运。

**这里有一处我们必须说清楚的诚实边界**：这 30 条内容是我们按母问题逐条比对过的，**当前没有一条直接指向「在校生找第一段 AI 产品实习」**——它们会全部被排除在三维图之外，图上显示「公开来源 0 条」。这不是页面故障，而**正是这个产品要表达的缺口**：一个真实存在、但公开内容答不清楚的问题。产品的价值恰恰在于指出这块空白，然后去找能填上它的人。

**凭证边界**：知乎凭证只从服务端环境变量读取，不进前端、不进 URL、不进日志、不进仓库。

**降级诚实**：接口失败、额度耗尽或返回空数据时，界面如实提示或如实显示为空，不会静默伪造来源。

## 五、与知乎社区生态的契合点

**内容基础。** 知乎沉淀了大量第一手经历——「我投了多少份」「面试被问了什么」「这个项目到底有没有用」。这些是**活问题**天然的背景语料，也是别的平台不具备的资产。我们不绕开这些内容，而是把它们当作背景，然后明确指出它们回答不了的那部分。

**提问机制。** 知乎已经形成了成熟的「有人提问、有人回答」习惯。**活问题**把它推进到「按位置提问、可交叉比较、逐条可核对」的一步：从「谁有空谁来答」变成「谁经历过谁来答」，并且明确区分「一个人说的」和「多个人可以互相比较的」。

**回答形态。** 产品的终点不是一份自嗨的结论，而是**一份可以在知乎发布的回答草稿**——它由已确认的来源和当事人经历拼成，用户可以修改后自行发布。这让每一次参与都能回流到知乎的内容生态，而不是留在产品内部。

**补位而非替代。** 我们刻意不去做「AI 替你回答一切」。在知乎的语境里，这个产品的定位是：**AI 负责把问题问清楚，人负责回答只有人能回答的部分。**

## 六、对社区用户的实际价值

1. **解决一类真实存在、目前无人解决的问题。** 正在找第一段实习的学生，今天只能看到「要怎么写简历」这类建议，看不到别人完整的失败过程。**活问题**把这件事变成一次可参与、可比较的调查。
2. **让「我经历过」这件事第一次被结构化地记录。** 身份、条件、结果、卡点，全部留痕且可横向比较。这不是又一次匿名发帖。
3. **不制造幻觉，是可以被信任的工具。** 公开内容不足就如实显示不足，只有一份经历就说「还不能说明普遍情况」，出现相反经历就保留矛盾，不取平均。
4. **给愿意分享的人一个低门槛的贡献方式。** 不需要写长文、不需要露脸，回答 5 至 6 个问题就完成了一次对陌生人的真实帮助，而且可以选择匿名。
5. **可复现、可审计。** 31 项浏览器端到端验收全部实跑通过，规则表开源在仓库中，任何人都可以逐行核对我们的判断逻辑，而不是相信一个黑盒。

## 附一、诚实边界（我们明确不做的事）

- **不伪造**知乎来源、匹配率或当事人经历；公开内容不足时如实显示为 0，并说明这是检索结果。
- **不把单条个人经历标成普遍事实**，只有一份就明确标注「还不能说明普遍情况」。
- **不自动发布**任何内容到知乎；回答草稿只生成给用户自己修改和决定。
- **不编造数字**，页面上出现的每一个统计值都来自当前真实数据。
- **静态资源白名单**：源码、数据、脚本、日志、配置一律不通过 HTTP 提供，目录穿越一律 404。
- **默认可嵌入性关闭**，需要时由环境变量显式放行。
