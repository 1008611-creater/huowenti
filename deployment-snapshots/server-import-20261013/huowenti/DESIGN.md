# 活问题 产品与设计记录

## 产品事实

- 产品：活问题 Living Question
- 核心承诺：AI 负责把问题问清楚、把已知和未知分开；答案由真正经历过的人提供，可比较、可核对。
- 当前阶段：可运行、已公网部署的 Web 产品，JSON 持久化，知乎官方接口可选接入。
- 母问题：2027 届普通本科生找第一段 AI 产品实习到底有多难？
- 主用户流程：活问题现场 → 三个缺口 → 参与采访 → 追问 → 贡献确认 → 问题变化 → 当前调查结论 → 知乎回答。

## 为什么是「活」问题

一个活问题有三个特征：

1. **它现在答不完整。** 公开内容里有方法，但没有一个具体的人从投递到被拒或被录用的完整经过。
2. **它会主动找人。** 问题按位置拆成四类身份，只问每个人知道的那一部分。
3. **它会随新经历变化。** 每一份确认后的经历都会改变六条子命题的覆盖状态，并可能发现下一处未知。

## 六条子命题

固定拆法，保证不同人的经历可以横向比较。

| 子命题 | 需要读到的内容 |
| --- | --- |
| 初始背景 background | 学校背景、专业、已有实习和已有项目 |
| 项目经历 project | 项目是否可运行、是否有真实用户、个人贡献是什么 |
| 投递过程 apply | 投递渠道、投递数量、目标公司类型 |
| 面试筛选 screen | 简历反馈、面试阶段、具体淘汰位置 |
| 公司差异 company | 大厂、成熟公司和 AI 创业公司的判断差异 |
| 最终结果与失败过程 result | 最好进度、Offer 情况、做过但没有产生效果的准备 |

## 四类参与身份

顺序为 `gained → rejected → seeker → recruiter`。

| 身份 | 问题数 | 进入的子命题 | 对调查的作用 |
| --- | --- | --- | --- |
| 我已经拿到实习或进入面试 gained | 6 | project / screen / result | 补充成功路径，并生成寻找条件相近失败者的对照任务 |
| 我投递过，但没有结果 rejected | 6 | apply / screen / result | 补充失败过程，推动区分学历、公司类型、项目可验证性与简历表达 |
| 我正在找第一段 AI 产品实习 seeker | 5 | background / apply | 增加需求信号，决定下一步优先调查什么 |
| 我参与过招聘或面试 recruiter | 5 | screen / company | 补充招聘方视角，验证或推翻求职者对淘汰原因的猜测 |

## 证据模型

判定按**六条子命题分别计算**，只有四种状态，全部可解释：

| 状态 | 触发条件 | 含义 |
| --- | --- | --- |
| `multi-case` 已有多份经历 | 当事人经历 ≥ 2 份 | 可以开始比较条件差异 |
| `single-case` 只有一份经历 | 当事人经历 = 1 份 | 还不能说明普遍情况 |
| `public-only` 只有公开讨论 | 无当事人经历，但有相关公开内容 | 缺少当事人提供的完整过程 |
| `empty` 覆盖不足 | 两者都没有 | 当前检索范围内覆盖不足 |

判定顺序是：先看当事人经历（多份 → 一份），再看公开内容，最后才是覆盖不足。这个顺序体现产品立场：**当事人的完整过程比公开讨论更有价值，但只有一份时仍然不能说普遍。**

## 相关性判据只有一套

同一个关键词表同时用于两处：

- 三维图上挂哪些公开内容（`classifySource`）
- 提出新问题时判断这个领域够不够（`currentCorpusHits`）

只有当内容**直接指向母问题**才算相关：实习 / 实习生 / 求职 / 找工作 / 秋招 / 春招 / 校招 / 应届 / 应届生 / 简历 / 面试 / 笔试 / 招聘 / 应聘 / 内推 / 投递 / offer / 毕业生 / 本科 / 本科生 / 大学生 / 在校生 / 就业 / 产品经理 / 第一段实习。

**泛职场词一律排除**（职场 / 职业 / 工作 / 升职 / 加薪 / 职业倦怠 / 职业发展）。原因很直接：这些词会让「如何让老板给我升职加薪」这类内容和母问题挂在一起，而它根本不回答这个问题。两处用同一套判据，才能保证「图上显示的相关条数」和「新问题判定里说找不到相关讨论」不互相矛盾。

## 覆盖不足是产品要表达的内容

当前公开内容底账 30 条，按母问题逐条比对后**没有一条直接相关**，因此三维图上显示「公开来源 0 条」。

这不是故障，而是结论本身。页面会直接把这句说明写在图上：

> 已按「在校生找第一段 AI 产品实习」逐条比对当前可检索到的公开内容（共 30 条，全部不指向在校生找第一段实习，已排除），没有一条写清一个具体的人在这一步的完整经过。这处空白是本次调查要填的部分。

三个缺口也遵循同一逻辑：**能读到的部分写清来源，读不到的部分如实留空。**

## 设计原则

- **缺口优先**：先展示读不到什么，再展示能读到什么。缺口不是营销话术，是去找人的理由。
- **按位置提问**：招聘一侧不会被问「你投了多少份」，求职者不会被问「你们怎么筛简历」。
- **确认后才进入**：贡献卡逐条列出用户提供的事实并标注来源，用户确认前不进入调查，且可以随时删除。
- **不伪造**：公开内容不足就显示为 0 并解释原因；只有一份经历就说不能说明普遍情况。
- **可解释**：出现相反经历就保留矛盾并标为对照，不取平均。

## 动效与页面设计

遵循公开的 motion-web 设计规范，并已落到代码、可被自动化验收检查：

- **时长阶梯 6 档**：instant 90ms / fast 170ms / standard 320ms / medium 460ms / slow 700ms / cinematic 1200ms
- **真实弹簧缓动**：CSS `linear()` 描述欠阻尼弹簧（stiffness 60–90、damping 0.86–0.93），入场有轻微过冲
- **帧率无关的跟随**：视角跟随按 `1-exp(-k·dt)` 计算
- **滚轮惯性防护**：累积 90px 触发、锁定 600ms、速度按 0.92 衰减
- **静止呼吸**：不同元素用不同频率的微光，避免整页同步闪烁
- **reduced-motion 三级降级**：位移动画降为纯淡入、呼吸与微光停止、过渡全部关闭，**内容照常出现**

**粒子是细小星光点，不是泡泡或球体**——硬约束。

## 当前明确不做

- 自动读取用户 GPS。
- 批量抓取知乎完整回答。
- 凭空生成当事人经历、匹配率或统计数据。
- 把单条个人经历标成普遍事实。
- 自动把任何内容发布到知乎。
